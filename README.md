# Конвейер данных грейдера: получение через API и загрузка в локальную базу

Грейдер - редактор кода внутри обучающей системы: студент пишет решение, запускает его, отправляет на проверку и получает баллы. Каждая попытка уходит на сервер и остается там. У сервера есть API, который отдает эти данные.

## Описание

Проект направлен на создание ETL‑пайплайна грейдера для онлайн-университета. Во время обработки в текстовой файл сохраняется лог работы скрипта с отлавливанием всех ошибок и выводом промежуточных стадий, именуемый в соответствии с текущей датой. Сохраняются логи за последние 3 дня.

## Цели и задачи

Цель – собрать данные о попытках студентов в свою локальную базу (PostgreSQL), чтобы считать по ним метрики и не нагружать боевой API каждый раз.

Задачи:

- Понять, что реально приходит в ответе и как разбирать скрытые поля.
- Придумать проверки, чтобы в базу не попадал мусор.
- Разложить записи в таблицу.
- Сделать повторный запуск безопасным.
- Вести лог, по которому видно, что происходит.

## Описание данных

API отдает массив записей. В каждой пять полей: `lti_user_id`, `passback_params`, `is_correct`, `attempt_type`, `created_at`.

Три нужных поля спрятаны внутри `passback_params` – это строка, похожая на словарь Python: `oauth_consumer_key`, `lis_result_sourcedid`, `lis_outcome_service_url`.

Период выгрузки – с 01.10.2022 по 01.06.2026. Объем – около 8,5 млн записей, порядка 3 ГБ в базе. Персональных данных нет.

Время в API приходит в UTC. В базе `created_at` хранится с часовым поясом, а сервер настроен на `Europe/Moscow`, поэтому в запросах время показывается по Москве – считать активность по часам и дням можно без пересчетов.

## Логика работы

Прежде чем приступить к написанию кода, я проверила, что реально отдает API и с какой скоростью. За сутки в 2026 году приходит около 500 записей, в 2023-м – до 10 тысяч. При этом любой запрос занимает не меньше 20 секунд, независимо от объема данных.

Из замеров выросли четыре решения, которые определили всю конструкцию:

- Качать окнами – весь период одним запросом не вытянуть.
- Проверять запись до вставки, а не разбираться с мусором потом.
- Защитить базу от дублей на уровне схемы, чтобы повторный запуск ничего не ломал.
- Писать лог – иначе двухчасовую выгрузку невозможно контролировать.

## Стек

- Python 3.14, зависимости через `uv`
- PostgreSQL 17
- `requests` – запросы к API
- `psycopg2` – драйвер PostgreSQL
- `python-dotenv` – чтение `.env`
- `gspread` – запись в Google Sheets
- Стандартная библиотека: `logging`, `argparse`, `datetime`, `pathlib`, `ast`

## Как работает

- Скрипт идет по периоду окнами по 14 дней.
- На каждое окно – один запрос к API, в ответ приходит список записей.
- Каждую запись проверяем: есть ли `id` пользователя, разбирается ли `passback_params`, известен ли тип попытки, сходится ли оценка с типом, разбирается ли дата.
- Плохие записи пропускаем и пишем в лог. Хорошие вставляем пачками по 10 000.
- Итог: сколько окон, сколько вставлено, сколько дублей, сколько отброшено.
- После загрузки считается агрегат по дням и записывается в Google Sheets: попытки, отправки, успешные, доля успешных и число уникальных студентов.
- После успешной загрузки отправляется письмо с итогом: сколько строк вставлено, сколько было дублей и сколько заняла выгрузка.

```
API ──> api_client.py ──> transform.py ──> loader.py ──> PostgreSQL
              │                │                │
              └────── logging_setup.py ─────────┘
```

## Как запустить

Нужны Python 3.14, `uv` и PostgreSQL 17.

```
git clone <https://github.com/EkaterinaDyuke/grader-etl.git>
cd grader-etl
uv sync
```

Создать базу и таблицу:

```
psql -U postgres -c "CREATE DATABASE grader_stats;"
psql -U postgres -d grader_stats -f src\schema.sql
```

Скопировать `.env.example` в `.env` и заполнить: ключ API и доступ к базе.

Google Sheets необязателен: без ключа скрипт отработает, но таблица не обновится. Чтобы включить, нужен сервисный аккаунт в Google Cloud: его JSON-ключ кладется в `secrets\google-key.json`, а в `.env` указываются путь к ключу и идентификатор таблицы. Таблицу надо расшарить на email сервисного аккаунта с правом редактирования.

Полный прогон – весь период, около двух часов:

```
uv run python src\main.py
```

Короткий прогон, чтобы проверить, что все работает:

```
uv run python src\main.py --start "2026-05-01 00:00:00" --end "2026-06-01 00:00:00"
```

Посмотреть результат в базе:

```sql
select count(*) from grader_attempts;
select attempt_type, count(*) from grader_attempts group by 1;
```

## Решения

- **14-дневное окно.** Сначала планировалось однодневное окно, но оказалось, что сервер тратит около 22 секунд на любой запрос, и 1 340 дней превращались в 11 часов. Я замерила время на 7 и 30 днях, посчитала, остановилась на 14.
- **Проблема дублей.** Решена со стороны базы данных. В таблице стоит `UNIQUE` на `user_id`, `lis_result_sourcedid`, `attempt_type`, `created_at`, а вставка идет с `ON CONFLICT DO NOTHING`. Повторный запуск безопасен: то же окно второй раз даст 0 вставок и N дублей.
- **Временная зона.** Время UTC. В описании API сказано, что сервер работает в нулевом поясе. Также косвенно это подтверждается активностью по часам. Если бы время было московское, то мы бы наблюдали высокую активность в 6 утра, что неестественно.
- **Период: с 01.10.2022 по 01.06.2026.** Начало по фактическим данным: в сентябре 2022 записей нет, в середине октября уже есть. Конец – 1 июня 2026. Данные за более поздние даты в API тоже есть, но их немного, и в текущий набор они не вошли.
- **Агрегаты пересчитываются целиком при каждом запуске.** Для 7 миллионов строк это около минуты, зато таблица всегда совпадает с базой: не бывает ситуации, когда данные догрузились, а агрегаты остались старыми.

## Что выяснилось про данные

- `oauth_consumer_key` внутри `passback_params` всегда пустая строка – проверять «заполнено» нельзя.
- 4 записи за день приходят без `user_id` и без `passback_params` (такие пропускаются).
- У 31 записи из дневной выборки нет `lis_outcome_service_url`, остальные поля целые, поэтому запись сохраняем, а поле оставляем `NULL`.
- `is_correct` приходит числами 0 и 1, а не `true`/`false`.
- `passback_params` – строка, похожая на словарь Python, поэтому разбирается через `ast.literal_eval`, а не `json.loads`.

## Результат

Полный прогон занял 2 часа 3 минуты – 96 окон. В базе 7 086 780 строк за период с 02.10.2022 по 31.05.2026 (последняя попытка – 31 мая в 23:52 UTC).

Из них:

- вставлено при прогоне – 7 066 637;
- дублей – 20 143: это май 2026, загруженный раньше при проверке, повторный запуск его не задвоил;
- отброшено – 34 700 (0,5%): записи без `user_id` или без `passback_params`.

Агрегаты за 1338 дней выгружены в Google Sheets.

## Ограничения

- Персональных данных нет: `user_id` – хеш, имен и адресов в ответе нет.
- Данные исторические, после 1 июня 2026 в выгрузку не входят.
- Скорость ограничена сервером: около 1 200 записей в секунду и ~22 секунды на запрос.
